## FAILURE 1 — TNA "Gold Standard" comparison broken

### 1. Where is the TNA fetch code and what URL pattern does it use?

**File:** `scripts/legislation/ingest.ts` — function `fetchTnaCompiledText()` (approx. line 197 post-changes).

**URL pattern:**
```
https://www.legislation.gov.uk/{legislationGovUkId}/section/{sectionNumber}/data.xml
```

For Equality Act 2010 s.11 this resolves to:
```
https://www.legislation.gov.uk/ukpga/2010/15/section/11/data.xml
```

`legislationGovUkId` = `ukpga/2010/15` (built by `buildLegislationGovUkId()` from feedUrl + year + number).
`sectionNumber` = the raw `<Pnumber>` value extracted from the CLML XML, typically `"11"`.

### 2. Raw TNA response

Not fetched during this audit (read-only). The response format for TNA data.xml at the section level returns a CLML XML document. **This is the most important unknown** — see diagnosis below.

**Recommended manual check:**
```
curl "https://www.legislation.gov.uk/ukpga/2010/15/section/11/data.xml" > V2.75_tna_eq_s11_raw.xml
```

### 3. The cleaning pipeline

`fetchTnaCompiledText()` in `ingest.ts`:

1. **Fetch** `https://www.legislation.gov.uk/ukpga/2010/15/section/11/data.xml`
2. **Strip all XML tags:** `xml.replace(/<[^>]+>/g, ' ')`
3. **Collapse whitespace:** `.replace(/\s+/g, ' ').trim()`
4. **Entity decode:** `&amp; → &`, `&lt; → <`, `&gt; → >`, `&nbsp; → ' '`, `&#xD; → ''`, `&#x9; → ' '`
5. **Write to R2** at key `ukpga/2010/15/sections/11.compiled.txt`
6. **Update DB** `compiledTextKey`, `compilationStatus: COMPILED`, `compiledBy: 'tna-direct'`

**The critical weakness**: step 2 strips ALL XML tags globally — it does not first isolate the `<P1group>` for section 11. If the TNA data.xml response contains content beyond section 11 (e.g., the full act, a chapter, or navigation elements), all of that text will be included in the "compiled" output.

### 4. Root cause hypothesis for "40B Employment Rights Act 2025" appearing

**Most likely: TNA data.xml for a section-level URL returns more than just that section.**

When TNA's `/section/11/data.xml` is requested, TNA may return:
- The full Act XML document (all sections, schedules, cross-references), **or**
- A chapter/part containing s.11, **or**
- A document including editorial notes and amendment cross-references mentioning other Acts

Employment Rights Act 2025 is a recent Act that amended several existing Acts. TNA's compiled version of Equality Act 2010 s.11 may include editorial notes like "amended by Employment Rights Act 2025 s.40B" or similar. After stripping all XML tags, these notes appear as plain text at the top or dispersed through the content, and if the section's own text is short or empty, the editorial note text dominates.

**Alternative hypothesis**: The `sectionNumber` `"11"` extracted from CLML may not be TNA's canonical identifier for this section. TNA sometimes uses different reference formats (e.g., `"11A"`, schedule references, or cross-part numbering). If TNA returns a 404 or wrong section for `/section/11/data.xml`, the response body may be an error page or redirect page whose text content gets stored verbatim.

**Does "40B Employment Rights Act 2025" appear elsewhere in the codebase?** Grep of the codebase found no hardcoded occurrence — the string must originate from a TNA API response stored in R2.

### Summary of Failure 1

The gold standard content is corrupt because `fetchTnaCompiledText()` strips all XML tags from the full TNA data.xml response **without first isolating the target section's XML node**. If TNA's section-level data.xml returns a document larger than one section (full act, chapter, or editorial notes), the compiled text will contain content from other sections or cross-referenced Acts. The string "40B Employment Rights Act 2025" almost certainly originates from amendment editorial content in a TNA response that included more than just the target section. **Fetching the raw response URL is the critical next step.**

## FAILURE 2 — Compile worker idling

### 1. Exact PENDING query in compile worker

File: `scripts/legislation/compile.ts` lines 286–290:

```typescript
const pendingSections = await prisma.legislationSection.findMany({
  where: { compilationStatus: CompilationStatus.PENDING },
  select: { id: true },
  take: 50,
})
```

It queries for sections where `compilationStatus === 'PENDING'` exactly. It takes at most 50 per run.

### 2. How many sections are in LegislationSection, grouped by status?

This audit cannot query Railway directly. The compile worker's log provides indirect evidence:
- **8908 COMPILED** in DB
- **0 PENDING** remaining (as reported by worker)
- **19783 total in DB** (reported by worker as `totalInDb`)

By subtraction: 19,783 − 8,908 COMPILED − 0 PENDING = **10,875 sections in some other status**.

The real target is ~180,000 sections (full corpus), meaning ~160,000 sections have not yet been ingested.

### 3. Intended state machine and why PENDING query misses sections

**Intended status transitions:**

```
[not in DB] → (ingest upsert) → PENDING
PENDING → (ingest: TNA text found) → COMPILED           [compiledBy: 'tna-direct']
PENDING → (compile.ts picks up) → COMPILING → COMPILED  [compiledBy: model name]
PENDING → (compile.ts error) → FAILED
COMPILED → (no further transitions in current code)
NEEDS_REVIEW → (manual review) → COMPILED
```

**The COMPILING status is the critical gap.** In `compileSection()` (compile.ts line 186):
```typescript
await prisma.legislationSection.update({
  where: { id: sectionId },
  data: { compilationStatus: CompilationStatus.COMPILING },
})
```

The compile worker sets a section to `COMPILING` before calling Gemini. If the worker restarts (manually or due to crash) while sections are in `COMPILING`, those sections are permanently stuck — the PENDING query does not match them. They will never be compiled.

### 4. Sections stuck in non-PENDING state

The 10,875 non-COMPILED, non-PENDING sections are almost certainly in `COMPILING` status. This would occur if:
1. The compile worker ran and set sections to `COMPILING`
2. The worker restarted (or crashed) before they completed
3. On the next run, those sections are invisible to the PENDING query

Additionally: the 0 PENDING count is also explained by a simpler scenario — **all currently-ingested sections had TNA compiled text and were marked COMPILED by the ingest script**. The ingest marks a section COMPILED immediately when it successfully fetches TNA compiled text. If every section of every ingested act had TNA text available, there would be legitimately 0 PENDING sections — the compile worker would have nothing to do. The remaining ~160,000 sections don't exist in DB yet (ingest incomplete).

**Which scenario is it?**

The 19,783 total vs 8,908 COMPILED leaves 10,875 unaccounted. If these are stuck in COMPILING, there IS work to do. If they are FAILED (from failed TNA+AI compilation attempts), `--reset-failed` would restore them. If they are in `NEEDS_REVIEW`, the worker does pick those up in the test-sections query but not in the compile query.

**Recommended DB query to run on Railway:**
```sql
SELECT "compilationStatus", COUNT(*) 
FROM "LegislationSection" 
GROUP BY "compilationStatus";
```

### 5. R2 spot-check (sections in R2 with no Railway row)

Cannot be performed without R2 API access during read-only audit. However, given the ingest architecture (R2 write always precedes DB upsert), it is possible for R2 keys to exist without a DB row if the script crashed between `r2Put()` and `prisma.legislationSection.upsert()`. The Prisma retry helper added in V2.75-A mitigates this going forward, but existing orphaned R2 keys from the crash are possible.

### Summary of Failure 2

The compile worker is not truly "done" — the most likely cause of 0 PENDING is that sections progressed to COMPILING status during a previous compile run and became stuck when the worker restarted. The PENDING query does not match COMPILING. A DB status breakdown (query above) is needed to confirm. If ~10,875 sections are stuck in COMPILING, the fix is to run `prisma.legislationSection.updateMany({ where: { compilationStatus: 'COMPILING' }, data: { compilationStatus: 'PENDING' } })` to unblock them — but this must be a deliberate manual step, not automated, since a running compile worker legitimately uses COMPILING as an in-progress marker.

## FAILURE 3 — Ingest crashed on Prisma P1017

### 1. Path confirmation

`scripts/legislation/ingest.ts` — confirmed. The ingest imports prisma from `../../scrutinise-web/lib/prisma`.

### 2. Prisma client construction (`lib/prisma.ts`)

Full client construction (`scrutinise-web/lib/prisma.ts`):

```typescript
import { PrismaClient } from '@prisma/client'
import { PrismaPg } from '@prisma/adapter-pg'

const globalForPrisma = globalThis as unknown as {
  prisma: PrismaClient | undefined
}

function createPrismaClient() {
  const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL! })
  return new PrismaClient({ adapter })
}

export const prisma = globalForPrisma.prisma ?? createPrismaClient()

if (process.env.NODE_ENV !== 'production') globalForPrisma.prisma = prisma
```

**No connection pool configuration is set.** `PrismaPg` default pool size is typically 10 connections. There is no `connectionTimeoutMillis`, `idleTimeoutMillis`, or `max` parameter set. Railway Hobby plan enforces its own connection timeout; long idle gaps between Prisma calls will trigger a server-side connection close (P1017).

### 3. Prisma call frequency per act

For a typical act with 30 sections where TNA compiled text is available for all:

| Operation | Calls |
|---|---|
| `legislationItem.upsert` | 1 |
| `r2Exists(xmlKey)` per section | 30 |
| `legislationSection.upsert` per section | 30 |
| `r2Exists(compiledKey)` per section | 30 |
| `legislationSection.update` (compiled-in-R2 path) | 30 |
| `legislationItem.update` (sectionCount) | 1 |
| **Total Prisma calls** | **92** |

For sections requiring TNA fetch, each section also has: `throttle.wait()` (200ms–5000ms), `fetch(tna url)`, then a `legislationSection.update`. The TNA fetch gap (200ms–5000ms per section) creates idle periods where the Prisma connection can time out. For an act with 30 sections at 5000ms throttle, the total TNA fetch time alone is 150 seconds — well above typical Railway idle connection timeouts.

### 4. Ingest log evidence

`ingest.log` is not present in the repository — the script logs to stdout only. There is no persisted log file from the crashed run. The crash at act 1891 (Administration of Justice Act 1982) is confirmed by the checkpoint file, which has 1,891 entries ending at `ukpga/1982/54` (the last few entries processed before the crash).

### 5. Fix applied (V2.75-A)

`withPrismaRetry()` has been added to `ingest.ts` and wraps all 6 Prisma calls in `ingestAct()`. On P1017 or P1001: waits 5 seconds and retries up to 3 times. A top-level try/catch in `main()` prevents any single act failure from stopping the loop. See V2.75-A section below for full details.

### Change 2 — withPrismaRetry helper as written

```typescript
async function withPrismaRetry<T>(fn: () => Promise<T>, label: string): Promise<T> {
  const RETRYABLE = ['P1017', 'P1001']
  for (let attempt = 1; attempt <= 3; attempt++) {
    try {
      return await fn()
    } catch (err: any) {
      const code = err?.code ?? ''
      if (RETRYABLE.includes(code) && attempt < 3) {
        console.warn(`  ⚠ Prisma connection drop on ${label} — retrying in 5s (attempt ${attempt}/3)`)
        await new Promise(r => setTimeout(r, 5000))
      } else {
        throw err
      }
    }
  }
  throw new Error(`withPrismaRetry: exhausted retries for ${label}`)
}
```

Wraps all 6 Prisma calls in `ingestAct()`:
1. `prisma.legislationItem.upsert` — label `upsert LegislationItem {id}`
2. `prisma.legislationSection.upsert` — label `upsert section {id}/{n}`
3. `prisma.legislationSection.update` (compiled-in-R2 path) — label `update section compiled-in-R2 {id}/{n}`
4. `prisma.legislationSection.update` (TNA text path) — label `update section TNA {id}/{n}`
5. `prisma.legislationItem.update` (sectionCount) — label `update LegislationItem sectionCount {id}`

The resume/skip check is **checkpoint-based only** (not DB-based). In `ingestAct()`:

## Executive summary

**Failure 1 (gold standard corrupted):** The cleaning pipeline strips all XML tags from the raw TNA response without first isolating the target section's XML node. TNA's section-level `data.xml` endpoint appears to return content beyond the requested section — likely editorial notes or cross-references from the Employment Rights Act 2025 that amends the Equality Act. The gold standard stored in R2 for s.11 is therefore that extraneous content rather than the section text. **Fix needed: fetch the raw TNA response for `/ukpga/2010/15/section/11/data.xml` and inspect it; then update `fetchTnaCompiledText()` to isolate only the relevant `<P1group>` node before stripping tags.**

**Failure 2 (compile worker idle):** The compile worker only queries for `PENDING` sections. Sections set to `COMPILING` by a previous crashed run are permanently stuck and invisible to the worker. The 10,875 non-COMPILED sections are almost certainly in `COMPILING` state. Additionally, all 8,908 currently-ingested sections may legitimately have TNA compiled text (COMPILED), making 0 PENDING correct for the current DB state — the remaining 160,000 sections simply haven't been ingested yet. **Immediate fix: run the DB status breakdown query; if COMPILING sections exist, manually reset them to PENDING via `updateMany`.**

**Failure 3 (P1017 crash):** The Prisma client has no connection pool or idle timeout configuration. Railway closes long-idle connections during TNA fetch delays (up to 5s × 30 sections = 150s per act). V2.75-A adds `withPrismaRetry` with 5s retry × 3 attempts and a per-act try/catch to continue on unrecoverable failures. The checkpoint file (1,891 acts) ensures the resume starts from act 1892.
