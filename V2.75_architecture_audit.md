## EXECUTIVE SUMMARY (read this first)

**Q1 — Are we storing original-as-enacted XML, or section-endpoint XML?**  
Neither. The R2 `.xml` files contain `<P1group>` sub-elements extracted from TNA's **current-version full-act CLML** (the `data.xml` link from the Atom feed, which returns the live/in-force text). These P1groups carry TNA in-force dates in their `DocumentURI` attributes (e.g. `2026-03-01`) and contain **zero amendment markup** (`<Addition>`, `<Substitution>`, `<Repeal>` tags are absent). This is not Layer 1 (original-as-enacted) and is not Layer 3 (TNA section endpoint XML). It is the current-compiled text of the section, scoped to the P1group node, from the full-act current-version download.

**Q2 — Is the AI compile pipeline producing usable summaries or mongrel?**  
Mongrel for the Layer 5 use case, possibly useful for a different purpose. The AI is receiving already-compiled TNA text (current state, tags stripped) and re-outputting it as a prose paragraph. Since zero sections have amendments recorded in the DB's amendment table, Gemini echoes the source text with subsection numbers run inline ("1 2 3 a b c"). The output is not verbatim statutory text, not a plain-English summary, and not the product of deterministic amendment application. It is a tag-stripped prose rendering of the current statutory text.

**Q3 — Is there any deterministic find-and-replace compilation?**  
None whatsoever. The entire "compile" pipeline is LLM-only (Gemini 2.5 Flash + Claude Haiku fallback). No XML parser library (`xml2js`, `fast-xml-parser`, `xmldom`, `DOMParser`) is used in any TypeScript source file. No code reads `<Addition>`, `<Substitution>`, or `<Repeal>` tags. Layer 5 (deterministic compiler) does not exist in this codebase.

## CHANGE 3 — Ingest Pipeline Audit

### 3.1 URL pattern for raw XML

The ingest does NOT hit a per-section URL for the raw XML. It fetches the **full act** CLML:

```typescript
// ingest.ts line 298–299
const clmlRes = await fetch(act.clmlUrl)
const clmlXml = await clmlRes.text()
```

`act.clmlUrl` is extracted from the TNA Atom feed entry:
```typescript
// ingest.ts line 96
const clmlUrl = entry.match(/<link[^>]*type="application\/xml"[^>]*href="([^"]+)"/)?.[1] ?? ''
```

This resolves to URLs like:
```
https://www.legislation.gov.uk/ukpga/2017/3/data.xml
https://www.legislation.gov.uk/ukpga/2010/15/data.xml
```

These are TNA's **current-version** full-act CLML endpoints — not the enacted version, not a section-level endpoint.

### 3.2 Trace for one act

**Example: Digital Economy Act 2017 (ukpga/2017/3)**

1. **Feed URL hit:** `https://www.legislation.gov.uk/ukpga/data.feed` (or tier-1 variant) — TNA Atom feed, paginated.
2. **Full-act CLML fetch:** `https://www.legislation.gov.uk/ukpga/2017/3/data.xml` — returns ~1MB+ XML document containing all sections in CLML format, current-version-as-in-force.
3. **Section extraction** (`fetchSectionsFromXml`): Regex `/<P1group>([\s\S]*?)<\/P1group>/g` extracts each P1group. For s.107EC:
   - `rawXml` = the full `<P1group>...</P1group>` XML block (stored as-is to R2)
   - `sectionNumber` = `107EC` (from `<Pnumber>`)
   - `sectionTitle` = `Section 107EA orders: further provision` (from `<Title>`)
   - `originalText` = P1group XML stripped of all tags (stored to Railway)
4. **R2 write:** `ukpga/2017/3/sections/107EC.xml` ← raw P1group XML
5. **Railway write:** `LegislationSection` row with `rawXmlKey`, `originalText`, `compilationStatus: PENDING`
6. **TNA section endpoint fetch:** `https://www.legislation.gov.uk/ukpga/2017/3/section/107EC/data.xml` (returns HTTP 404 for this section)
   - If 404: section stays PENDING → picked up by compile.ts
   - If 200: P1group scoped, stripped → stored to `.compiled.txt` R2 key → `compiledBy: 'tna-direct'`

### 3.3 Original-as-enacted URL (not used by current script)

TNA's original-as-enacted CLML endpoint is:
```
https://www.legislation.gov.uk/ukpga/2017/3/enacted/data.xml
```

The current script never hits this URL. There is no `enacted` suffix, no `?version=enacted` parameter, and no changes-over-time API call anywhere in the codebase.

**To get original-as-enacted XML with `<Addition>/<Substitution>/<Repeal>` amendment markup**, TNA provides:
- The "revised with effects shown" view at section level: `/{id}/section/{N}/data.xml?showingEffects=true` (or similar — exact parameter not confirmed, but TNA's editorial annotation appears in their revision history CLML)
- Alternatively, TNA's changes-to-legislation API

The current ingest has no code path for either.

### 3.4 Does the ingest preserve amendment markup?

**No.** The raw XML stored in R2 is the P1group from TNA's current-version CLML, which already has all amendments applied. TNA's live `data.xml` endpoint does not include `<Addition>/<Substitution>/<Repeal>` tags — those appear only in TNA's editorial/revision views. The `fetchSectionsFromXml` function stores the P1group verbatim, which correctly preserves CLML structure elements (`<P2>`, `<P3>`, `<Text>`, `<UnorderedList>`, `<Term>`, `<Citation>`) but these are structural, not amendment markup.

## CHANGE 6 — Legislation-compare Page Audit

### 6.1 What two strings are compared via Jaccard?

`s.compiledText` (gold, from R2) vs `aiText` (fresh LLM output):

```typescript
// LegislationCompareClient.tsx lines 68–81
function tokenise(text: string): Set<string> {
  return new Set(
    text.toLowerCase().replace(/[^a-z0-9\s]/g, ' ').split(/\s+/).filter(Boolean)
  )
}

function jaccardSimilarity(a: string, b: string): number {
  const setA = tokenise(a)
  const setB = tokenise(b)
  const intersection = new Set([...setA].filter(x => setB.has(x)))
  const union = new Set([...setA, ...setB])
  if (union.size === 0) return 0
  return intersection.size / union.size
}

// Line 290–292
const aiText = await caller(SYSTEM_PROMPT, userPrompt, apiKey, modelId)
const score  = goldText ? jaccardSimilarity(goldText, aiText) : 0
```

Jaccard is computed on **word-token sets** (case-folded, punctuation removed). This is a bag-of-words similarity measure, not an order-sensitive measure. Two texts with the same words in different orders score 100%.

### 6.2 Where do the strings come from?

**Gold text (`compiledText`):** `route.ts` line 31: `r2Get(s.compiledTextKey)` — fetched from R2 `.compiled.txt` at page load. This is either:
- A TNA section endpoint text (if `compiledBy === 'tna-direct'`) — stripped-tag current text from TNA's section endpoint
- An AI-compiled text (if `compiledBy === 'gemini-2.5-flash'` or `'claude-fallback'`) — Gemini/Claude output from a previous compile run

The compare page UI labels this "Gold standard (TNA / AI compiled)" which is accurate but potentially misleading — AI-compiled text is not a gold standard for verifying AI outputs.

**AI text (`aiText`):** Generated fresh on each evaluation run via direct browser-to-provider API calls (Gemini, Anthropic, OpenAI, xAI, etc.). No caching.

**User prompt passed to the model (`buildUserPrompt`):** Uses `s.originalText` (from Railway DB — the tag-stripped text from the full-act CLML fetch), not the R2 `.xml` file. Also passes amendments from the DB.

### 6.3 Is the AI Output pane a fresh re-compile or stored R2 value?

**Fresh per evaluation run.** The component calls the provider API directly from the browser on each "Run evaluation" click. The stored R2 `.compiled.txt` is used ONLY as the gold standard, never displayed as the AI Output pane.

### 6.4 Source of each pane for the test sections

**Test sections source:** `GET /api/legislation/test-sections` → Railway query: `compilationStatus IN [COMPILED, NEEDS_REVIEW]` AND `compiledTextKey IS NOT NULL`, ordered by `createdAt ASC`, limit 20. These are the 20 oldest ingested sections with compiled text.

**"TNA Gold Standard" pane:** Misleadingly named. For most sections this is TNA-direct compiled text (tag-stripped P1group from TNA section endpoint). For the 5,507 AI-compiled sections that appear in the first 20, the gold standard would be AI output — not TNA.

**"AI Output" pane:** Fresh LLM call on each test run, using `originalText` from Railway and `amendments` from DB (empty for all current sections).
