## PART 2 — Worker throughput by worker number (not by corpus)

### Problem
Email shows throughput by corpus label. Charlie wants it by WORKER_ID (1–20).

### Root cause
`ingest_progress_snapshots` stores `workerLabel` (corpus name) not `workerId` (1–20).
Workers don't write their WORKER_ID into the snapshot.

### Fix — two changes:

**2a — Schema: add workerId column**
```sql
-- Migration: add workerId to ingest_progress_snapshots
ALTER TABLE ingest_progress_snapshots ADD COLUMN "workerId" integer;
```
Create migration file: `scrutinise-web/prisma/migrations/20260603220000_snapshot_worker_id/migration.sql`
Update both Prisma schemas.

**2b — Scheduler: populate workerId when writing snapshots**
The scheduler aggregates per-worker data from the queue. It needs to track which
WORKER_ID produced which rows. Currently it groups by `workerLabel`.

Change: when writing snapshots, include the numeric worker ID derived from 
`process.env.WORKER_ID` on each worker. Since the scheduler runs centrally, it
should query `ingest_progress_snapshots` grouped by workerId, not workerLabel.

Workers themselves need to write per-worker snapshots — not the scheduler.
Move snapshot writing from scheduler into worker-queue.ts:
```typescript
// In worker-queue.ts, after every N sections processed (e.g. every 100):
await writeProgressSnapshot({
  workerId: parseInt(process.env.WORKER_ID ?? '0'),
  workerLabel: `Worker ${process.env.WORKER_ID}`,
  sourceKey: currentRow.sourceKey,
  sectionsCompiled: sessionSectionsCompiled,
  sectionsEstimated: 0, // scheduler fills this in
})
```

**2c — Email format change**
In `progress-reporter.ts`, find `queryWorkerThroughput()`.
Read only that function (~40 lines, search by name).

Change grouping from `workerLabel` to `workerId`.
New email format:

Show: worker number, current source, sections/hr, efficiency vs theoretical max.
Flag workers below 40% efficiency as ⚡low. Flag workers at 0 as ℹ️ idle.

## PART 4 — "No format" explanation + fix

### Context
`null` in format breakdown = format column was never set on that queue row.
~99,617 rows affected. These are rows processed before format-tracking was added,
or from source clients that don't set the format field.

### Fix
For rows where format is null but status is done, backfill format from the
R2 key pattern or from the corpus name:
```sql
-- Backfill format for TNA legislation rows (they use CLML)
UPDATE ingest_queue SET format = 'clml'
WHERE format IS NULL 
  AND status = 'done'
  AND corpus LIKE '%primary-acts%' OR corpus LIKE '%si-%' OR corpus LIKE '%regional%';

-- Backfill for caselaw (HTML)
UPDATE ingest_queue SET format = 'html'
WHERE format IS NULL AND status = 'done' AND corpus = 'tna-caselaw';
```

Run these SQL statements, report how many rows updated. This cleans up the
format breakdown without any code changes.
