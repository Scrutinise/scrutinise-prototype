## PART 2 — Scheduler email deduplication (definitive fix)

### Problem
Every scheduler run sends two emails — one new-format, one old-format.
CC confirmed loop() called once, one Railway service. Yet two emails fire.

### Definitive fix — process-level lock
Add a DB-based lock at the start of each scheduler run. If the lock is held
by another process, abort immediately. This prevents any double-firing
regardless of the underlying cause.

```typescript
// In scheduler.ts, at the start of run():
async function acquireSchedulerLock(): Promise<boolean> {
  try {
    // Use upsert with a unique key — only one process can hold it
    await prisma.$executeRaw`
      INSERT INTO scheduler_lock (id, locked_at, process_id)
      VALUES (1, NOW(), ${process.pid})
      ON CONFLICT (id) DO UPDATE
        SET locked_at = NOW(), process_id = ${process.pid}
        WHERE scheduler_lock.locked_at < NOW() - INTERVAL '50 minutes'
    `
    // Verify we hold the lock
    const lock = await prisma.$queryRaw<{process_id: number}[]>`
      SELECT process_id FROM scheduler_lock WHERE id = 1
    `
    return lock[0]?.process_id === process.pid
  } catch {
    return false
  }
}
```

Add migration for `scheduler_lock` table:
```sql
CREATE TABLE scheduler_lock (
  id INTEGER PRIMARY KEY DEFAULT 1,
  locked_at TIMESTAMPTZ NOT NULL,
  process_id INTEGER NOT NULL,
  CONSTRAINT single_row CHECK (id = 1)
);
```

In `run()`, wrap entire function:
```typescript
async function run(): Promise<void> {
  const hasLock = await acquireSchedulerLock()
  if (!hasLock) {
    console.log('[scheduler] another instance holds the lock — skipping this run')
    return
  }
  // ... rest of run()
}
```

This means even if two instances are somehow running, only one sends an email per hour.
