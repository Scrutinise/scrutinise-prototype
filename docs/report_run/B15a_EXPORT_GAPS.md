## 3. ⚠⚠ The third gap, and it runs the *opposite* way to the one you asked me to watch for

You asked me to report anything on the screen that is not in the JSON. **On M-01 the reverse is
true: the screen shows zero for data the export now carries.**

The facts strip on M-01 reads, live, after a hard reload:

> **Issues: 0 raised · 0 resolved · 0 open** · **Known unknowns: 0 declared** · **Last deepening run:
> never**

while the database holds **89 issues, 8 `RUN` passes and 20 known unknowns** for that same idea.

**The cause, traced to the line.** `buildFacts()` in `lib/lex/deepening.ts:191` counts issues
*through* the pass list — `passes.flatMap(p => p.issues)` — and the Deepening layer's canonical
`PASS_KEYS` (`deepening-config.ts:436`) are five:

```
EVIDENCE_PRECEDENT · LEGAL · FINANCIAL · POLITICAL_RISK · STATUTORY_CONSEQUENCES
```

The rows **the build writes** carry entirely different keys:

```
pass:SMART_VOCABULARY · question:LINEAGE · question:CAUSE_SEEDING · question:CAUSAL_EVIDENCE
question:DOMAIN_TRANSFER · question:EXISTING_POWER · question:LEGAL_LANDSCAPE · question:CASE_INTERPRETATION
```

**Two producers write to one table in two key vocabularies, and the reader knows only its own.** So
the build's 89 challenges are real, stored, and invisible on the Research panel.

That also explains your screen: **"3 · The Deepening — 2 passes run, 30 issues open" cannot have been
M-01**, which reports `never`. It will have been an idea whose Deepening was run through its own
flow, under the canonical keys.

⚠ **This is the sixth-or-seventh instance of the same shape this week** — a reader whose scope is
narrower than the data it reads — and it is the first one where the *product* is the loser rather
than a harness. **The 89 challenges are the report's raw objection material and a user cannot see
them.** Not fixed today: it is a product change, not a run change, and CLAUDE.md §12 applies.
