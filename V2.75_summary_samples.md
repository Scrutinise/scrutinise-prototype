## CHANGE 2 — Where summaries come from

### Which script writes `.summary.txt` files?

**`scripts/legislation/compile.ts`** — the lexSummary step runs inside `compileSection()`, lines 225–235, immediately after the compiled text is written to R2.

Summary generation is **not** in `ingest.ts` and there is no separate summary script. It is part of the AI compilation pipeline and only fires for sections that go through the AI path (gemini-2.5-flash or claude-fallback) — which is why only 1,142 of the 40,635 sections have `.summary.txt` files.

### The prompt (verbatim from `compile.ts` lines 40–41 and 227–229)

**System prompt (`SUMMARY_SYSTEM_PROMPT`):**
```
You are a legal analyst. Produce a clear, plain English summary of what this section of UK legislation says and does. Write 2-4 sentences suitable for a non-lawyer. Do not reproduce the statutory language verbatim.
```

**User prompt (constructed at runtime, line 229):**
```
Summarise this section: {compiledText sliced to first 3000 chars}
```

The summary is generated from the **compiled text** (the Gemini JSON `compiledText` output — the tag-stripped version of the section), not from the raw XML. It calls `callGeminiText()` (plain text response, not JSON), using the `SUMMARY_SYSTEM_PROMPT` and the compiled text.

### Are summaries generated as part of compile.ts, ingest.ts, or a separate script?

**`compile.ts` only.** `ingest.ts` never writes to `.summary.txt` keys. There is no third script. Summary generation is a secondary step inside `compileSection()` — it only runs if the primary Gemini JSON call succeeds, and its failure is caught and logged without failing the section compilation. The `lexSummaryKey` field in the DB is set to the R2 key if the summary write succeeded, or left `null` if it failed (compile.ts lines 241–244).
